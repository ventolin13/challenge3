# Сопроводительное описание

Черновик письма. В основном о том, что менять, когда перевод монет живёт в игре, а не в тестовом задании. Как устроен сам сервис — в `docs/kak-est.md`.

## Что менять для продакшена

Сначала зафиксировать нагрузку: пик переводов в секунду, допустимую задержку `POST` и `GET`, число аккаунтов, долю чтений баланса к записям. Повтор запроса не имеет права провести перевод дважды. Потерю и двойное списание монет в допуск не закладывать. В задании этих чисел нет: десять аккаунтов и `localhost:3000`.

Пока оба `balance` и строка перевода пишутся вместе, хватает одного Postgres. Запись перестаёт помещаться на один мастер — счета делить по `account_id`. Чтение баланса само по себе вторую базу не требует.

Запись перевода и изменение `balance` — только мастер. Проверка «хватит ли средств» и чтение уже записанного перевода — тоже мастер. Реплика годится для показа баланса на экране, если короткая задержка допустима. После своего перевода клиент читает баланс с мастера или дожидается события.

Один сценарий «перевод монет» остаётся одним процессом. Отдельный процесс появляется вместе со своей базой: инвентарь предметов, уведомления, вебсокеты.

Между этими сервисами — gRPC. Снаружи для клиента игры остаётся HTTP.

Двухфазное подтверждение между сервисом монет и сервисом предметов не использовать. Каждый фиксирует только свои строки. Перевод монет в той же транзакции пишет исходящее событие. Инвентарь применяет его отдельно и по идентификатору перевода не применяет второй раз.

Это событие — outbox: строка в той же транзакции Postgres, что балансы и перевод. Отдельный процесс публикует её в очередь. Сбой публикации не откатывает уже сохранённый перевод. Очередь несёт «перевод исполнен» в инвентарь и в уведомления. Она не заменяет `idempotency_key`. Сообщение может прийти дважды, обработчик идемпотентен по `transfer_id`.

«Тебе перевели монеты» и «предмет продан» шлёт отдельный контур по событию из очереди, не хендлер `PostTransfer`.

Вебсокет держит отдельный процесс на тех же событиях: игрок видит баланс и входящий перевод без опроса. HTTP остаётся источником истины, после события клиент может перечитать `GET /api/v1/accounts/{id}`.

У аккаунта для обмена предметами нужно количество каждого предмета: сколько в инвентаре и сколько выставлено на продажу. Продажа — одна операция: у продавца количество на продажу не меньше покупаемого, оно уменьшается, инвентарь покупателя растёт, монеты списываются у покупателя и зачисляются продавцу. Подарок без предмета остаётся нынешним `POST /api/v1/transfers`.

## Почему эта база, фреймворк и библиотеки

Postgres. Перевод — это два `balance` и одна строка, их нужно фиксировать вместе. Для суммы есть `numeric`, для запрета отрицательного остатка — `CHECK (balance >= 0)`.

gin. Контракт задания — три HTTP-ручки, сервис один.

pgx — доступ к Postgres. squirrel — сборка SQL. Сумма в сервисе — `decimal`, в базе `numeric(20,2)`. Миграции — Flyway. Проверки в тестах — testify. Описание ручек — swag, интерфейс на `http://localhost:3000/swagger/index.html`.

## Инфраструктура, деплой, масштаб

Локально один `docker-compose`: сервис на порту 3000 и Postgres. Начальные `acc_1` … `acc_10` включаются флагом только в этом запуске. В продовом запуске флаг выключен, повторный старт балансы не меняет.

Дальше тот же один процесс за балансировщиком, Postgres с мастером и репликой. Масштаб записи — вертикально, затем шардирование по `account_id`. Масштаб показа баланса — реплика. Уведомления, вебсокеты и инвентарь подключаются через outbox и очередь, когда появятся свои данные.

## Компромиссы

В сервисе у аккаунта только баланс монет. Предметов на продажу, очереди, outbox, уведомлений и вебсокетов нет: контракт задания их не содержит.

Идемпотентность — строка `TransferModel`, исполненный перевод или нехватка средств. Отдельной записи ключа нет. `self-transfer not allowed` и `account not found` в базу не пишутся.

Сериализация и взаимная блокировка — один 409 `transfer transaction rolled back, retry the request`. Сервис транзакцию заново не открывает, повтор решает клиент. Уже занятый `transfer_id` — отдельный 409. Нет соединения с Postgres — 500 `postgres connection failed`.

Блокировка `SELECT … FOR UPDATE` берётся на исходящий аккаунт. Входящий `balance` увеличивается в SQL на `amount`. `created_at` в ответе nullable. `amount` и `balance` на проводе — JSON-числа, в базе — два знака после запятой.
